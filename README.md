# Campus Market

Campus Market is a student-to-student marketplace for buying, selling, and giving away
items on campus — textbooks, electronics, lab gear, and more.

This version runs as a production-style web app with a real backend: accounts and passwords,
listings, a server-side cart, checkout/orders, buyer↔seller chat, notifications, favorites,
and an administrator dashboard are all persisted in a SQLite database instead of localStorage.

## Quick start

You need [Node.js](https://nodejs.org) **22.5 or newer** (for the built-in `node:sqlite`
module — see "How the backend works" below).

```bash
cd campus-market
npm start
```

Then open **http://localhost:3000** in your browser.

That's it — there is nothing to `npm install`. The server creates its SQLite database
automatically on first run.

## Getting started

To create an account, use the Sign Up page at **http://localhost:3000/signup.html**. 
New accounts require verification before they can post listings or make purchases.

### Create an admin account

Use the setup script to create or promote an admin account:

```bash
node server/setup-admin.js admin@campus.com SecurePassword123 "Admin Name"
```

Then sign in at **http://localhost:3000/admin-login.html** with those credentials to access the admin panel at **http://localhost:3000/admin.html**.

## What's actually backed by the server now

| Feature | Before | Now |
|---|---|---|
| Accounts | Fake — any password worked | Real signup/login, passwords hashed with `scrypt`, sessions are signed tokens |
| Listings | Hardcoded JS array + unposted "Sell" form | Persisted in SQLite; "Sell an item" really creates a row, photos are saved as real files on disk |
| Cart | `localStorage` | Stored server-side per account, so it follows you across devices/browsers |
| Checkout / Orders | Fake, just wrote to `localStorage` | Real orders + order line items in the database; marks listings as sold/claimed; notifies the seller |
| Messages | Canned, static conversation | Real conversations + messages between real accounts, persisted, with unread counts and lightweight polling |
| Notifications ("Alerts") | Canned list | Real notifications generated by real events (new message, item purchased/claimed, welcome) |
| Favorites ("Saved Items") | Not implemented | Real per-account favorites |
| Categories / Safe zones | Static config | Left as static front-end config on purpose — this is rarely-changing reference data, not user data |

## How the backend works

It's a small Node.js HTTP server with **zero external dependencies** — nothing to
`npm install`, nothing that can fail to download. That's possible because it only uses
things built into modern Node:

- **`node:sqlite`** (built into Node 22.5+) for the database — no native compilation,
  no separate database server to run.
- **`node:http`** with a tiny hand-rolled router (`server/lib/http-helpers.js`) instead
  of Express.
- **`node:crypto`** for password hashing (`scrypt`) and for signing session tokens
  (a JWT-style `header.payload.signature` token, HMAC-SHA256) — no `jsonwebtoken` or
  `bcrypt` package needed.

```
server/
  server.js            entry point — wires everything together, serves the frontend too
  lib/
    db.js              SQLite connection + schema
    auth.js            password hashing, session tokens
    http-helpers.js     router, static file server, JSON helpers
    seed.js            (production: no seeding)
    uploads.js         saves photos from the "Sell" form to server/uploads/
    format.js          shared serialization / relative-time helpers
  routes/
    auth.js            POST /api/auth/signup, /login, GET /me
    products.js        listings: list/search, get, create, edit, delete
    cart.js            server-side cart
    orders.js          checkout + order history
    messages.js        conversations + chat
    notifications.js   alerts feed
    favorites.js       saved items
  uploads/             photos uploaded through the Sell form land here
  data/                campus-market.db (created on first run, not checked in)
```

The existing frontend (plain HTML/CSS/JS, no build step) is served by the same process —
`server.js` serves the static files at the project root, so the whole app runs from one
`npm start` on one port. The only new frontend file is `assets/js/api.js`, a small `fetch()`
wrapper that every page now uses instead of reading/writing `localStorage` directly.

### A couple of deliberate, low-risk design choices

- **Session caching:** after login, the JWT-style token and a copy of the user's public
  profile are cached in `localStorage` purely so pages can do an instant "am I logged in?"
  check without an extra round trip. The token itself is still independently verified by
  the server on every single API call — the cache is just a UX convenience, not the source
  of truth for authorization.
- **Photo uploads:** the "Sell an item" form already turned chosen photos into base64 data
  URLs in the browser (for the instant preview). Rather than adding a multipart/form-data
  parser, the backend accepts those same data URLs in the JSON body and writes them to
  `server/uploads/` as real files — so listings get real persisted images with no extra
  moving parts.
- **Categories & safe zones** stay as static frontend config (`assets/js/products.js`).
  They're a fixed taxonomy that doesn't belong to any one user, so there's no real benefit
  to a database table for them — the meaningful "backend" work went into accounts,
  listings, cart, orders, chat, notifications, and favorites instead.

## API overview

All endpoints are under `/api`. Authenticated routes expect `Authorization: Bearer <token>`.

```
POST   /api/auth/signup            { name, email, studentId, password }
POST   /api/auth/login             { identifier, password }
GET    /api/auth/me

GET    /api/products               ?q=&category=&type=free|trade&mine=1&saved=1
GET    /api/products/:id
POST   /api/products               { title, category, price, isFree, description, location, images[], verification }
PUT    /api/products/:id
DELETE /api/products/:id

GET    /api/cart
POST   /api/cart                   { productId, qty, size, color }
PATCH  /api/cart/:itemId           { qty }
DELETE /api/cart/:itemId

POST   /api/orders                 { zone, meetupTime, paymentMethod }
GET    /api/orders
GET    /api/orders/:id

GET    /api/conversations
POST   /api/conversations          { otherUserId, productId }
GET    /api/conversations/:id
POST   /api/conversations/:id/messages   { body }

GET    /api/notifications
POST   /api/notifications/read-all

GET    /api/favorites
POST   /api/favorites/:productId
DELETE /api/favorites/:productId
```

## Hosting and deployment

This project is ready to be hosted on a Node.js platform such as Render, Railway, Fly.io, or a VPS.

### Recommended Render setup

- Create a web service from this repository.
- Use the start command: `npm start`
- Set the port to `10000` or let the platform inject it automatically.
- Mount a persistent disk at `/var/lib/campus-market` and set:
  - `CAMPUS_MARKET_DATA_DIR=/var/lib/campus-market`
  - `NODE_ENV=production`
- Create an admin account once the app is deployed:
  - `node server/setup-admin.js admin@your-domain.com StrongPassword123 "Admin Name"`
- (Optional) Enable real password-reset emails instead of showing the code on screen — see [Password reset emails](#password-reset-emails) below.

A deployment template is included in [render.yaml](render.yaml).

### Password reset emails

By default, "Forgot password" generates a real 6-digit code but has nowhere to send it (the app has zero external dependencies), so the code is shown directly on screen instead — fine for local development and demos.

To send the code by real email instead:

1. Create a free account at [resend.com](https://resend.com) and generate an API key.
2. Set these environment variables on your host:
   - `RESEND_API_KEY=re_your_key_here`
   - `MAIL_FROM=Campus Market <noreply@yourdomain.com>` (optional — defaults to Resend's shared test sender, which only delivers to the email address you signed up to Resend with; verify your own domain in Resend for delivery to any address)
3. Redeploy. Once `RESEND_API_KEY` is set, the code is emailed and withheld from the API response — the on-screen fallback only appears when email isn't configured or a send fails.

No new npm dependency is required — email is sent with a direct HTTPS call to Resend's API using Node's built-in `https` module (see `server/lib/mailer.js`).

### Production notes

- The app uses a local SQLite file and will persist it at the directory pointed to by `CAMPUS_MARKET_DATA_DIR`.
- The server exposes a health endpoint at `/api/health` for uptime checks.
- The app runs in a single Node process and is suitable for Render, Railway, Fly.io, or a VPS.

## Notes / known limitations

- `node:sqlite` is still flagged "experimental" by Node — it works well here, but if a
  future Node release changes its API, pin to Node 22.x.
- Chat updates via polling every 4 seconds while a thread is open, not WebSockets — simple
  and dependency-free, with a small delay rather than instant delivery.
- There's no payment gateway integration (Mobile Money / card on the checkout page are
  recorded as the buyer's chosen method, not actually charged) — consistent with the
  original prototype, which was never wired to a real payment provider either.
